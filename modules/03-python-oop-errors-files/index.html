Errors are messages, not verdicts

When Python hits something impossible, it stops and prints a traceback — a map of exactly where it was when things broke. Beginners see a wall of scary text; professionals see the two most useful lines first. The rule: read it bottom-up. The last line says what went wrong, the lines above say where.

Handling errors: try / except

Sometimes an error is expected — a user types "abc" where a number should be — and crashing is the wrong response. try/except lets you attempt something and catch a specific failure:

text = "3.7x"          # imagine this came from a messy CSV

try:
    value = float(text)
except ValueError:
    value = None        # our chosen "couldn't parse" signal

print(value)             # None — program continues, no crash

Catch the narrowest exception that you actually expect — except ValueError:, not a bare except:, which would also silently swallow typos and genuine bugs. You can also raise your own: raise ValueError("temperature below absolute zero") — turning a silent bad value into a loud, early, well-labeled failure.

Files: reading and writing data

Every ML project starts by reading data from disk. The idiom to memorize is with open(...) — the with block (a context manager) guarantees the file is properly closed even if an error occurs mid-read:

with open("scores.txt", "w") as f:     # "w" = write mode
    f.write("90\n85\n77\n")

with open("scores.txt") as f:           # default mode is read
    scores = [int(line) for line in f]   # a file is a sequence of lines!

print(scores)                            # [90, 85, 77]

Classes: why model.fit() looks the way it does

A class bundles data and the functions that operate on that data into one unit. Each instance (object) carries its own data in attributes; methods are functions that automatically receive the instance as their first parameter — that's all self is. Here is a genuinely useful class: the simplest possible ML model, one that predicts the mean of whatever it was trained on:

class MeanModel:
    def fit(self, values):
        self.mean = sum(values) / len(values)   # learned "parameter"
        return self

    def predict(self):
        return self.mean

model = MeanModel()      # create an instance
model.fit([4, 8, 6])     # it "learns" (stores) the mean: 6.0
print(model.predict())   # 6.0

This is not a toy analogy — it's literally scikit-learn's API shape. Every model you'll use is a class; .fit() computes and stores learned parameters as attributes; .predict() uses them. A mean is even a real baseline model you'll compare against in Module 11.

Modules: using other people's code

  
A module is just a Python file you can import.
  The standard library ships hundreds; the ML stack (NumPy, pandas, scikit-learn)
  is "just" more modules:

  
import math                    # use as math.sqrt(2)
from statistics import mean    # or import one name directly

print(math.sqrt(2))            # 1.4142135623730951
print(mean([4, 8, 6]))         # 6 — the library version of our MeanModel!


  

    Math deep dive The exception hierarchy, dunder methods, and how import finds things
    

      
Exceptions form a class hierarchy. ZeroDivisionError
      is a subclass of ArithmeticError, which is a subclass of
      Exception. An except ArithmeticError: clause catches its
      subclasses too — which is exactly why except Exception: is almost always
      too broad: it catches nearly everything, including bugs you wanted to hear about.

      
Dunder ("double underscore") methods are how classes plug into
      Python's syntax. len(x) secretly calls x.__len__();
      a + b calls a.__add__(b); print(x) uses
      x.__repr__(); and MeanModel() itself calls
      __init__ if defined. When NumPy arrays support a + b or
      a @ b in Module 07, it's these hooks doing the work — operator syntax in
      Python is method calls wearing nicer clothes.

      
How import finds modules: Python walks the directories
      in sys.path — the script's own folder, then installed packages
      (site-packages, where pip puts things). That's precisely why our notebooks do
      sys.path.append(...) to reach shared/notebook_utils: we're
      adding one more place to look. Compiled bytecode is cached in
      __pycache__ folders — safe to ignore and to gitignore.

    

  


  
Worked example

  
All four topics in eight lines — a robust file-loading function:

  
def load_scores(path):
    scores = []
    with open(path) as f:               # file (auto-closed)
        for line in f:
            try:
                scores.append(float(line))   # may fail on messy lines
            except ValueError:               # narrow catch
                print("skipping bad line:", line.strip())
    return scores

  
Given a file containing 90, 85, oops,
  77, it returns [90.0, 85.0, 77.0] and prints one warning —
  instead of crashing on line three. This skip-don't-crash pattern is 80% of real-world
  data loading.


  

    
Common pitfalls

    
Bare except: — catches everything, including
    the bug you're currently hunting. Always name the exception you expect.

    Forgetting self — writing def fit(values):
    inside a class gives the confusing error "fit() takes 1 positional argument but 2 were
    given": the instance is silently passed as the first argument, and there was no
    self to receive it.

    Shadowing built-ins — naming a variable list,
    sum, or max works... until three cells later when
    list(range(5)) mysteriously fails with "'list' object is not callable".
