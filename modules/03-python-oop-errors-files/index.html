Part 1 · Read the error

Errors are messages, not verdicts

Module 01 introduced the idea that an error is feedback, not a verdict, and showed you a two-line NameError. Here we go much further: you will learn to read a traceback of any length, in a script or in a notebook, and to answer the one question that actually matters — where is the mistake? — which is frequently not the line Python points at.

What Python does when it cannot continue

An exception is Python's way of reporting that it cannot carry out an instruction as written. When one happens, Python abandons the current line, abandons the function that line was in, abandons that function's caller, and keeps going up until either something handles the exception (Part 2) or it reaches the top of your program. If nothing handles it, Python stops and prints a traceback: a record of the chain of calls that was in progress, followed by the exception's type and message.

Every traceback answers exactly three questions, and it is worth naming them because beginners routinely read only the first:

1 · What

The last line: the exception type and its message. ZeroDivisionError: division by zero.

2 · Where

The frames above it: one file-and-line block per call in progress, oldest at the top, newest at the bottom.

3 · Why

Not printed anywhere. You infer it by asking which frame produced the bad value. That is the skill this part teaches.

Here is the full traceback from a real four-line program. Read it, then read the reading order underneath:

def average(values):
    total = sum(values)
    return total / len(values)

scores = []
result = average(scores)
print(result)
Traceback (most recent call last): File "analyze.py", line 6, in <module> result = average(scores) File "analyze.py", line 3, in average return total / len(values) ~~~~~~^~~~~~~~~~~~~ ZeroDivisionError: division by zero

Read it bottom-up

The heading says Traceback (most recent call last), and that sentence is the instruction manual. Python lists the calls in the order they happened, so the most recent — the one that actually broke — is at the bottom, right next to the exception. Reading a traceback top-down is like reading a detective novel backwards.

The bottom-up rule

① Last line. Read the exception type and message in full. Do not skim it; the message usually contains the offending value.
② The block just above it. That is the crash site: the exact file, line number, function name, and source line that raised. Python 3.11 and later also print ~~~^^^ markers under the precise sub-expression that failed.
③ Walk upward. Each block above is one caller further back. Stop at the lowest block that is in a file you wrote — that is where your best guess lives.

In the example: ① division by zero. ② len(values) was 0 inside average. ③ line 6 called average(scores), so scores was empty.

Notice the <module> in the first block. That is the name Python uses for code at the top level of a file — not inside any function. In a notebook you will see <module> for cell-level code too. And notice that the frames are indented two spaces with the source line indented four: that visual rhythm is how you count frames at a glance.

The crash site is not always the mistake

This is the most valuable idea in the whole part, so it gets its own name. The crash site is the line that raised. The root cause is the mistake that produced the bad value. They are frequently in different functions, written by different people, on different days.

In the example above, average is not wrong. total / len(values) is the correct formula for a mean. What is wrong is that average was handed an empty list on line 6. The fix therefore has two candidate homes:

Fix at the crash site — hides the problem

def average(values):
    total = sum(values)
    if len(values) == 0:
        return 0.0      # a silent lie
    return total / len(values)
0.0

Fix at the root cause — states the truth

def average(values):
    """Return the mean of values."""
    if not values:
        raise ValueError("average() needs at least one value")
    return sum(values) / len(values)
ValueError: average() needs at least one value

Is the mean of no numbers really 0.0? No — it does not exist. The left column returns a plausible-looking number that will travel silently into a report and be wrong there instead, one hundred lines further from the mistake. The right column refuses, at the boundary, with a sentence naming the problem. Part 3 shows how to write that raise; for now, simply notice that choosing where to fix a bug is a decision, and the traceback gives you the evidence to make it.

A useful habit: after reading a traceback, say out loud "it crashed here, but the bad value came from there." If you cannot finish the second half of that sentence, you have not finished reading.

  no sense at all, restart the kernel and run every cell from the top before debugging further.


  
Chained tracebacks


  
Sometimes Python prints two tracebacks joined by a sentence. That is a
  chained exception: one exception was caught, and a second was raised in its place,
  keeping the first as its cause. You will create these yourself in Part 3; you need to
  read them now.


  
Traceback (most recent call last):
  File "study_tracker.py", line 9, in parse_minutes
    return int(text)
ValueError: invalid literal for int() with base 10: 'thirty'

The above exception was the direct cause of the following exception:

Traceback (most recent call last):
  File "study_tracker.py", line 13, in <module>
    print(parse_minutes("thirty"))
          ~~~~~~~~~~~~~^^^^^^^^^^
  File "study_tracker.py", line 11, in parse_minutes
    raise InvalidEntryError(f"row 4: minutes must be a whole number, got {text!r}") from error
InvalidEntryError: row 4: minutes must be a whole number, got 'thirty'


  

    
How to read a chained traceback

    
The first block is the origin. Something concrete and low-level went
    wrong: int("thirty") failed.

    The bridge sentence tells you which kind of chain it is. "The above exception
    was the direct cause of the following exception" means a human deliberately wrote
    raise … from error. "During handling of the above exception, another exception
    occurred" means a second, accidental failure happened inside the
    except block — that second one is usually a bug in the error handler.

    The last line is what escaped. It is what a caller would have to catch, and
    it usually carries the friendlier message.

  


  
So a chained traceback is a gift: it gives you the business-level description
  (row 4: minutes must be a whole number) and the technical origin
  (invalid literal for int()) in one printout. Read the first block to fix the data
  and the last line to understand the contract.


  

    
Three ways beginners lose time on tracebacks

    
Scrolling past it. The commonest habit of all: see red, feel bad, jump
    straight back to the code and start changing things. The traceback already contains the answer
    roughly 80% of the time. Read all of it before touching the editor.

    Guessing instead of reading. "It's probably the loop" is not evidence. The
    line number is evidence. If you have made three changes without reading the new traceback each
    time, you are no longer debugging.

    Assuming the bottom frame is your bug. When the crash site is inside a library
    — a path such as C:\Python314\Lib\… or anything under
    site-packages — the library is almost certainly fine. Scan upward for
    the lowest frame in a file you wrote. That line is your call, and its arguments are the
    suspects. Case 3 of Demo 1 is exactly this shape.

TypeError vs ValueError


  
These two are the most-confused pair in Python, and the distinction is crisp once you hear it
  said properly:


  

    
Kind versus content

    
TypeError — the wrong kind of thing arrived. The
    operation is impossible for that type, whatever the value happens to be.

    ValueError — the right kind of thing arrived, but its
    content cannot be used. The operation makes sense for this type; not for this value.

  apart.


  
UnboundLocalError: the one that looks impossible


  
You met the cause of this in
  Module 02 · scope; here is
  the exception it produces, with its full modern message:


  
total = 0

def add_minutes(entries):
    for entry in entries:
        total = total + entry       # looks like it reads the global
    return total

print(add_minutes([45, 30]))

  
Traceback (most recent call last):
  File "study.py", line 8, in <module>
    print(add_minutes([45, 30]))
          ~~~~~~~~~~~^^^^^^^^^^
  File "study.py", line 5, in add_minutes
    total = total + entry
            ^^^^^
UnboundLocalError: cannot access local variable 'total' where it is not associated with a value


  
The message is doing you a favour by using the word local. Python decided
  at compile time that total is a local name in add_minutes, because the
  function assigns to it somewhere. That decision covers the whole function body,
  including the read on the right of the =, which happens first. So the read looks for
  a local that has not been created yet.


  
The fix is almost never the global keyword. It is to give the local a starting
  value, or better, to pass it in and return it:


  

    

      
Initialise the local

      
def add_minutes(entries):
    total = 0                # now it exists
    for entry in entries:
        total = total + entry
    return total

    

    

      
Better: no shared state at all

      
def add_minutes(entries):
    """Return the total of entries."""
    return sum(entries)

    

  


  
Older Pythons phrased this as local variable 'total' referenced before assignment.
  If you find that wording in a tutorial, it is the same error; the newer sentence is simply
  clearer about why the variable is local.

  Part 2 · Handle what you expect
  
try / except: expecting failure


  
Reading errors is half the skill. The other half is deciding, in advance, which failures your
  program should survive. That is what try/except is for — and it is
  routinely overused, so this part spends as much time on when not to as on the syntax.


  
When crashing is the wrong response


  
Split every possible failure into two piles:


  
    
    
  • An expected failure is one the outside world can legitimately cause and you can
    do something sensible about: a file whose fourth row has a blank number, a user who types
    abc into a numeric box, a network that is briefly down. There are thousands of
    such rows in real data. Crashing on row 4 of 20,000 is not robustness; it is fragility.
    • 
    
  • An unexpected failure is a bug in your own code: a typo, a wrong argument order,
    an attribute you forgot to create. These should crash, loudly, immediately, with a
    traceback you can read. Anything that suppresses them costs you hours.
    • 
  


  
The whole art is handling the first pile without accidentally silencing the second. Here is
  the minimal example, with the failure Module 01 taught you to read:


  
text = "3.7x"               # imagine this came from a messy CSV

try:
    value = float(text)
except ValueError:
    value = None            # our chosen "could not parse" signal

print(value)

  
None


  
The program continued. Note that value = None is a decision, not the
  only option — Part 3 argues that raising a named exception is usually better than a sentinel.
  What matters here is the mechanics.


  
Anatomy of a try statement


  

    
try:
    minutes = int(row["minutes"])
except ValueError as error:
    print("skipping row:", error)
else:
    total = total + minutes
finally:
    print("row handled")

    

      
try opens the protected block.
      Keep it as short as you can — ideally one risky line — because everything inside it is
      covered by the except clauses below.

      
except introduces a
      handler. It runs only if an exception occurred in the try block
      and matches the named type.

      
ValueError is the type being caught. Naming
      it is what makes this code honest: you are saying "I expect exactly this failure".

      
as error binds the exception
      object to a name so you can inspect it. Optional, and almost always worth writing.

      
else runs only if the try
      block finished without raising. It is where the "and now do the rest" work belongs.

      
finally runs no matter what: success,
      handled failure, unhandled failure, even a return. It is for cleanup.

      
Only try and one other clause are required. else and
      finally are optional and are covered in
      the third section of this part.

    

  


  
Catch the narrowest thing you can name


  
A bare except: catches literally everything. So does

Three ways try/except goes wrong

    
except Exception: pass — the silent-bug factory. This is the
    single most damaging two-line pattern in Python. It catches your typos, your wrong argument
    orders, and your AttributeErrors, then throws away the evidence. If you truly
    want to ignore a specific failure, name it and say why:
    except FileNotFoundError: pass  # first run, no cache yet.

    Catching too early. A low-level function that swallows an error and returns
    None removes the caller's ability to decide. Let the exception travel to the level
    that knows what to do — often the loop over rows, or main(). Handle where you have
    context, not where the error happens.

    Using try/except where an if would do.
    try: x = values[0] except IndexError: x = None is worse than
    x = values[0] if values else None. Exceptions are for the unusual; a possibly
    empty list is not unusual. The judgement call has a name — look-before-you-leap versus
    ask-forgiveness — and Part 3 gives you the rule.

    Design deep dive Why except Exception deliberately misses Ctrl-C
    

      
At the very root of the tree sits BaseException. Directly beneath it are four
      children, and only one of them is Exception. The other three are not errors at
      all — they are control-flow signals:

      
    
        
  • KeyboardInterrupt — you pressed Ctrl+C.
    • 
        
  • SystemExit — something called sys.exit().
    • 
        
  • GeneratorExit — a generator is being closed.
    • 
      

      
None of these means "the program went wrong". They mean "the program is being asked to
      stop". Python's designers put them outside Exception precisely so that
      the ordinary, everywhere-in-real-code pattern
      except Exception: — inside a loop over 20,000 rows, say — cannot accidentally
      make your program unstoppable.

      
A bare except: throws that protection away: it is equivalent to
      except BaseException:. Put one inside a long loop and
      Ctrl+C becomes a no-op — every press is caught, logged, and ignored.
      The only way out is to kill the process. This is why every Python style guide bans the bare
      form.

      
BaseExceptionGroup is the fourth child, added in Python 3.11 for reporting
      several failures at once. You will not need it in this course; it is mentioned only so the
      tree in Demo 3 does not look incomplete when you eventually read the official hierarchy in
      the documentation.

    

  


  
else and finally


  
Two optional clauses complete the statement. They exist to answer questions the two-clause
  form cannot: "what should happen only on success?" and "what must happen whatever occurs?"


  
else: only when nothing went wrong


  
An else block runs if — and only if — the try block finished without
  raising. Its purpose is to keep the try block down to the single line you are
  actually worried about:


  

    

      
Too much inside try

      
try:
    minutes = int(row["minutes"])
    total = total + minutes
    print("added", labels[minutes])
except ValueError:
    print("bad row")

    

    

      
One risky line, the rest in else

      
try:
    minutes = int(row["minutes"])
except ValueError:
    print("bad row")
else:
    total = total + minutes
    print("added", labels[minutes])

    

  


  
The columns look equivalent and are not. Suppose labels is a list and
  labels[minutes] raises — an IndexError, fine, both columns let it
  through. But suppose it is a lookup that raises ValueError for some inputs. In the
  left column, that failure is caught by a handler written for the parsing step and
  reported as bad row. You would hunt for a data problem that does not exist. The
  right column cannot make that mistake, because the except clause only ever sees
  line 2.


  

    
The try block belongs to the risky line, not to the task

    
Put in try only the code whose failure you named in the except
    clause. Everything that merely follows on from success goes in else.
    A one-line try is a sign of a well-written handler.

  


  
finally: whatever happens


  
A finally block runs on every path out of the statement: success, handled
  exception, unhandled exception, return, break, continue.
  It is for cleanup — releasing something you acquired, whatever the outcome:


  
handle = open("sample_log.csv", encoding="utf-8")
try:
    rows = handle.read().splitlines()
finally:
    handle.close()          # runs even if .read() raises
print(len(rows))


  
You will almost never write that in practice, because Part 5's with statement
  does exactly this for you and is shorter. But knowing what with does is the
  point: it is a try/finally in one line.


  
finally runs even past a return


  
Here is the fact that surprises everyone, and the reason this section exists. A
  return inside try does not skip finally. Python evaluates
  the return value, holds it, runs finally, and only then hands the value back:

        print("finally: always runs")

Raising: failing loudly and early


  
So far you have been on the receiving end of exceptions. Now you produce them. This is not an
  advanced technique to reach for occasionally — it is how every well-written function protects
  itself and its callers, and it is how the study tracker in Part 9 refuses bad rows.

The raise statement creates an exception and starts it travelling up the call

The habit to build: validate at the top of the function, before doing any work.
  This is often called a guard clause. It keeps the interesting code un-nested and

    """Return a (name, minutes) pair, rejecting unusable input."""
    if not name:
        raise ValueError("name must not be blank")
    if not isinstance(minutes, int):

    if minutes < 0:

Re-raising, and raise … from error


  
Often you want to catch a low-level failure, add context, and let it keep travelling. Three
  forms, in increasing order of usefulness:


  
# 1 · bare re-raise: log, then let the original continue untouched
try:
    minutes = int(text)
except ValueError:
    print("could not parse", repr(text))
    raise                      # same exception, same traceback

# 2 · replace it: the original is lost, which is usually a mistake
try:
    minutes = int(text)
except ValueError:
    raise InvalidEntryError(f"row {number}: bad minutes")

# 3 · chain it: your message on the outside, the original preserved
try:
    minutes = int(text)
except ValueError as error:
    raise InvalidEntryError(f"row {number}: bad minutes") from error

That works — and it is still the wrong tool here, for a reason that has bitten a great many

assert versus raise

    
assert — for a state you believe is impossible: a
    sanity check on your own logic, halfway through your own function. "By this point,
    self.mean_ must exist." Assertions document invariants and catch programming
    mistakes.

    raise — for anything a user, a file, or another program can
    cause. Bad input is not impossible; it is Tuesday.

    
The mechanical reason: running Python with the -O flag
    (python -O script.py) removes every assert statement from
    the compiled code. An assert guarding your input validation simply
    vanishes in that mode, and the bad row sails straight through. A raise never
    vanishes.

  


  
So use assert in notebooks and tests (the notebook's check and
  check_raises helpers are this idea, wrapped so a failure prints instead of stopping
  the kernel), and use raise in any function that touches data from outside your
  program.

        data = handle.read()
except FileNotFoundError:
    data = ""

    

  


  
EAFP is idiomatic Python, and for files it is also the only correct choice. The
  left column has a race condition: between the moment exists() answers
  yes and the moment open() runs, another program can delete or rename the
  file. Your check was true and your open still fails — and now it fails in the
  branch you thought was safe, with no handler. The right column asks the operating system to do
  the check and the open as one step, and handles the only answer that matters.


  
The same argument applies to dictionaries (try: d[k] except KeyError: versus
  if k in d:) with less urgency, since a dict cannot change underneath you. There the
  choice is about readability: use in or .get() when absence is ordinary,
  and try when it is genuinely exceptional. Do not use both — a membership test
  followed by a try for the same key is noise.

The rule that explains every FileNotFoundError

    
A path that does not start at the top of the disk resolves against the working
    directory — the folder Python was launched from. It does not resolve
    against the file you are editing, or the file containing the open() call.

    
So when a file you can plainly see cannot be found, the question is never “where is my file?”
    It is “where is Python standing?” Answer it with print(Path.cwd())
    before changing anything else.

Opening a file: the mode decides everything


  
open() takes a second argument, the mode — a short string saying
  what you intend to do. It is the most consequential argument in the standard library, because one
  of its values destroys data on sight.


  
open(path, "r", encoding="utf-8")   # read  — the default
open(path, "w", encoding="utf-8")   # write — EMPTIES the file
open(path, "a", encoding="utf-8")   # append
open(path, "x", encoding="utf-8")   # create, and refuse if it already exists


  
What open() returns is a handle: an object representing the connection to
  the file and remembering a position inside it. The mode fixes what that handle may do, at the
  moment it is created. Ask a read-only handle to write and the complaint arrives from a module you
  have probably never heard of:

Choosing a mode by intent


  

    
Say the intent out loud, then pick the letter

    
“Look at what is in there.” → "r", which raises if the file is
    missing — usually right, because a missing input is a real problem.

    
“This file must contain exactly what I am about to write.” →
    "w", for a regenerated summary whose old contents are worthless by definition.

    
“Add to a growing record.” → "a", for logs and for results
    accumulated across runs.

    
“Write a new file, and tell me if I am about to clobber something.” →
    "x", safest when the file name comes from data, a timestamp, or a user.

    FileExistsError → you used "x" and the file was there, which is
    "x" doing its job. io.UnsupportedOperation → mode and method

  Part 5 · Read and write real data
  
with open(...): the idiom to memorise


  
Every machine-learning project begins by reading data off a disk, and Python has one correct
  shape for it. Learn these two lines as a unit, the way you learned for:


  
with open(path, encoding="utf-8") as f:
    ...


  
Three promises are packed in: open gives you a handle, as f names it,
  and with guarantees the handle is closed on the way out. The third is the one you
  cannot see.


  
What with guarantees


  
An open file consumes an operating-system resource, and on Windows it holds a lock — another
  program, Excel for instance, may be unable to open the file until you let go. Worse, data you have
  written may still sit in a buffer, not on disk, until the handle closes. So every
  open needs a matching close; the question is who guarantees it.


  

    

      
Bare open — the close can be skipped

      
f = open("sandbox/out.txt", "w",
         encoding="utf-8")
f.write("90\n")
f.write(str(1 / 0))     # raises here
f.close()               # never runs

      
ZeroDivisionError: division by zero

The file stays open, and "90\n"
may never reach the disk.

    

    

      
with — closed no matter what

      
with open("sandbox/out.txt", "w",
          encoding="utf-8") as f:
    f.write("90\n")
    f.write(str(1 / 0))   # raises here

      
ZeroDivisionError: division by zero

The file is closed and flushed
first; "90\n" is safely written.

    

  


  
The exception escapes in both columns — with catches nothing and is no substitute
  for try/except. What it guarantees is cleanup,
  in every exit path: falling off the end, a return, a break, or an
  exception. It is the same “whatever happens” promise as
  finally, with none of the typing.


  

    
Two rules, no exceptions

    
Always with. If you find yourself typing f.close(),
    you have written the wrong shape.

    
Always encoding="utf-8". On every open, reading and
    writing alike. The next section explains what goes wrong without it; the
    rule is easier to keep than the explanation is to remember.

    
Keep the block short: read or write, then get out and work on the data. A handle held open
    across fifty lines of computation is a handle held open across fifty chances to raise.

  


  
Once the block ends the handle is dead, and the message is unmistakable:


  
with open("sandbox/scores.txt", encoding="utf-8") as f:
    pass

print(f.read())

  
ValueError: I/O operation on closed file.


  
That error nearly always means one mistake: the line using the data sits at the wrong
  indentation, outside the with block instead of inside it. Read it as “you are one
  indent level too far left.”


  
A file is a sequence of lines


  
A text handle is iterable, and iterating it yields one line at a time. This is the most
  useful fact about files, because every loop skill from Module 01 and every container skill from
  Module 02 applies
  immediately:


  
with open("sandbox/scores.txt", encoding="utf-8") as f:
    for line in f:
        print(repr(line))

  
'90\n'
'85\n'
'77\n'


  
Note the repr, following Part 3's habit: each line arrives
  with its newline still attached. That trailing \n is invisible in
  print(line) and causes a large share of “but they look identical” bugs. And because a
  file is iterable, a comprehension reads it in one line:


  
with open("sandbox/scores.txt", encoding="utf-8") as f:
    scores = [int(line) for line in f]

print(scores)

  
[90, 85, 77]


  
int("90\n") works because int() tolerates surrounding whitespace. Do
  not rely on that generosity: int("90 kg") raises
  ValueError: invalid literal for int() with base 10: '90 kg'.

  repeatable:


  
with open("sandbox/scores.txt", encoding="utf-8") as f:

['85', '77']

That is a feature when deliberate — f.readline() for a header, then a loop for the
  data — and baffling when not. If a “second pass” over a file comes back empty, this is why.


  
Line endings and .strip()


  
Every line a file yields ends with '\n', except possibly the last if the file does
  not end with a newline. str.strip() removes whitespace from both ends, including that
  newline, and is the standard first move on every line you read:


  
with open("sandbox/names.txt", encoding="utf-8") as f:
    names = [line.strip() for line in f]

print(names)

  
['maya', 'ravi', 'ada']


  
Without .strip() you get ['maya\n', 'ravi\n', 'ada'] — the third
  element differs from the first two, so names[0] == "maya" is False while
  names[2] == "ada" is True. That inconsistency is the worst kind of bug:
  it works on the last row of your test file and fails on every other.


  
Windows adds a layer. Files written by Notepad or Excel end lines with carriage return plus
  newline ('\r\n'); macOS and Linux use just '\n'. Python's text mode hides
  this by translating between them, which is called universal newlines. It helps everywhere
  except in one place, the csv module — which is exactly why newline=""
  exists.


  
Writing


  
.write() writes exactly the string you give it and adds nothing:
  no newline, no separator, no conversion.


  
with open(OUT / "scores.txt", "w", encoding="utf-8") as f:
    f.write("90")
    f.write("85")

print(repr((OUT / "scores.txt").read_text(encoding="utf-8")))

  
'9085'


  
Two values became one meaningless number because nothing separated them. Supply the newlines
  yourself:


  
with open(OUT / "scores.txt", "w", encoding="utf-8") as f:
    for score in [90, 85, 77]:
        f.write(f"{score}\n")        # the \n is yours to add

  
'90\n85\n77\n'


  
.write() also refuses anything that is not a string —
  f.write(90) raises TypeError: write() argument must be str, not int. And
  .writelines(list_of_strings) is not the plural convenience it appears to be: it adds no
  newlines either, so f.writelines(["a", "b", "c"]) produces 'abc'. Build
  them in: f.writelines(f"{s}\n" for s in scores).


  

    
Three writing mistakes, in order of frequency

    
Forgetting the newline. Reading the file back gives one enormous line. Check
    with repr(path.read_text(encoding="utf-8")).

    
Reading before the block closes. Written data may still be buffered, so a
    second handle opened inside the same with block can see an incomplete file. Finish
    writing, leave the block, then read.

    
Writing into the file you are reading. Opening the same path with
    "w" mid-read truncates it under your own feet. Read it all into memory, close, then
    write — or write to a new name and rename.

  


  
A robust loader


  
Real data has bad rows. A loader that crashes on the first one is useless; one that silently
  ignores them is worse. Combining Part 2's narrow catch with this
  section's iteration gives the pattern you will write for the rest of your career:


  
def load_scores(path):
    """Return the numbers in path, one per line, skipping unparseable lines."""
    scores = []
    with open(path, encoding="utf-8") as f:              # closed automatically
        for number, line in enumerate(f, start=1):       # 1-based line numbers
            try:
                scores.append(float(line))               # may fail on messy lines
            except ValueError:                           # narrow: only bad numbers
                print(f"line {number}: skipping {line.strip()!r}")
    return scores

print(load_scores("sandbox/messy.txt"))


  
Given a file containing 90, 85, oops, 77:

  
line 3: skipping 'oops'
[90.0, 85.0, 77.0]


  
    
    
  • The try wraps one line. Only float(line) can raise
    ValueError, so only it is protected.
    • 
    
  • The catch is ValueError, not Exception. A typo in
    scores.append raises AttributeError and must still reach you.
    • 
    
  • FileNotFoundError is deliberately not caught. A missing file is
    not a bad row — it is a broken call, and the caller needs to hear about it.
    • 
    
  • Skips carry their line number, via enumerate(f, start=1), so the
    message points at something you can go and look at. A silent continue is the
    difference between a warning and a mystery.
    • 
    
  • The !r calls repr, so a line containing only a stray
    space prints as ' ' rather than as nothing at all.
    •

  InvalidEntryError carrying the row number, and the caller decides whether to skip or
  stop.


  

    Optional deep dive What a context manager actually is
    

      
A context manager is any object that can appear after with. The
      protocol is two methods. When Python reaches the with line it calls the object's
      __enter__(), and whatever that returns is bound to the name after as.
      When the block ends — normally, via return or break, or because an
      exception is travelling upward — Python calls __exit__(), passing it details of the
      exception if there was one. For a file handle, __exit__ flushes the buffer and
      closes the descriptor. That is the entire mechanism: two methods with agreed names, which
      Python calls on your behalf.

      
Those double-underscore names are dunder methods, the general way ordinary
      classes plug into Python's own syntax; Part 6 introduces them properly.
      Because __exit__ sees the exception, a context manager can suppress it by
      returning a true value — that is how contextlib.suppress works — but a file handle
      does not, which is why the exception in the code-pair above still escaped. You will use context
      managers constantly and write one rarely; beyond files you will meet database connections,
      locks, and PyTorch's with torch.no_grad():, the same protocol turning gradient
      tracking off and reliably back on.

    

  


  
Text is bytes: encoding


  
A disk cannot store letters. It stores numbers, eight bits at a time. So every text file is
  really a sequence of numbers, and turning them back into characters requires knowing which rulebook
  was used to write them down.


  
Why a file of text needs a decoder ring


  
An encoding is that rulebook: a mapping between characters and the bytes representing
  them. Crucially, the file does not record which encoding was used. A
  .csv file is just bytes, so decoding with the wrong rulebook may produce no error at
  all — just wrong characters.


  
For plain English the choice barely matters, since almost every encoding agrees on
  a–z, the digits, and basic punctuation. It starts mattering the instant
  your data holds a name like José, a unit like µm, or a curly quote pasted
  from Word — which is to say, it starts mattering with real data. UTF-8 is the encoding
  that can represent every character in every writing system, and it is what the internet, macOS,
  Linux, Git, and most data files use. It is variable-width: ASCII characters take one byte,
  é takes two. That is why é is the character that breaks things — it is
  where the encodings stop agreeing.


  
Always pass encoding="utf-8"


  

    
The rule, and the Windows reason behind it

    
Every open() you ever write takes encoding="utf-8". Reading and
    writing. No exceptions.

    
Why it matters more on Windows. Omit encoding and Python picks a
    default from the operating system. On macOS and Linux that default is UTF-8, so the code appears
    to work. On a typical Windows 11 machine it is cp1252, a single-byte,
    Western-European-only encoding that cannot represent most of Unicode. This is the whole
    explanation for the most demoralising bug report in beginner Python: “it works on my
    colleague's Mac and crashes on my laptop.” The code is identical; the default is not.

    
Check yours if curious — import locale; print(locale.getpreferredencoding()) — but
    do not build on the answer. Passing encoding="utf-8" makes the machine
    irrelevant.

Symptom 1 — UnicodeDecodeError. The bytes make no sense under the
  rulebook you supplied, so Python refuses to guess. Here a file containing a Word curly quote is
  read as UTF-8:

Encoding traps

    
Omitting encoding entirely. The commonest cause. Your code becomes
    machine-dependent with no visible sign, and a colleague, a build server, or a future you on a
    different laptop finds out.

    
A CSV exported from Excel. Excel prepends three invisible bytes called a
    byte order mark (BOM). Read it with plain utf-8 and those bytes join your
    first column name, so the header is '\ufeffname' instead of 'name' and
    row["name"] raises KeyError: 'name' on a column you can see. Read such
    files with encoding="utf-8-sig", which strips the mark if present and is harmless if
    not; write with plain "utf-8".

    
“Fixing” mojibake by editing the text. Replacing Ã© with
    é patches one file and leaves the cause in place. Fix the encoding
    argument and re-read the original.

    
Assuming a file that opens correctly in Notepad is UTF-8. Notepad guesses, and
    its guess is not Python's. Only the encoding argument decides what your program
    sees.

CSV stands for comma-separated values: plain text in which each line is one record,

And why by hand breaks


  
Now suppose one topic contains a comma. The CSV convention wraps such a field in double quotes —

  drops the fifth value, and code checking len(row) == 4 discards the row. The same
  failure occurs with a quoted field containing a newline, which spreadsheets also produce. You could
  write the quote handling yourself — about forty lines with a dozen edge cases — but it has already
  been written correctly.

newline="", or you get blank lines on Windows


  

    
Every csv handle takes newline=""

    
The csv module writes its own line endings, '\r\n', because the CSV
    convention specifies them. Python's text mode also translates '\n' into
    '\r\n' on Windows. Both fire, so every line ending becomes '\r\r\n' and
    the file gains a blank line between every real row:

    
with open(OUT / "bad.csv", "w", encoding="utf-8") as f:      # newline="" missing
    csv.writer(f).writerows([["name", "minutes"], ["maya", "45"], ["ravi", "20"]])

print(open(OUT / "bad.csv", "rb").read())

    
b'name,minutes\r\r\nmaya,45\r\r\nravi,20\r\r\n'

    
Read that file back and the blank lines arrive as empty rows, which crashes any code doing
    int(row["minutes"]):

With newline="" the translation is off and csv does the job alone:
    b'name,minutes\r\nmaya,45\r\nravi,20\r\n'.

    
Pass newline="" when reading too. It costs nothing and protects
    you from a quoted field that legitimately contains a newline, which text mode would otherwise
    split across two records before csv ever saw it. Build one fixed habit:
    open(p, encoding="utf-8", newline="") for every csv handle in either
    direction.

  


  
Everything from a CSV is a string


  

    
The trap that produces the most TypeErrors in this course

    
A CSV file has no types. It is text. So DictReader hands you text, for every
    column, always — even for a column that obviously holds numbers:

    
with open(LOG, encoding="utf-8", newline="") as f:
    rows = list(csv.DictReader(f))

print(rows[0])

Look at the printed row: '45', in quotes. That single pair of quotes is the whole
    bug, and it is easy to skim past. sum(int(r["minutes"]) for r in rows) gives
    360; forget the int and sum(r["minutes"] for r in rows)
    raises TypeError: unsupported operand type(s) for +: 'int' and 'str'.

    
Worse are the operations that do not fail. "45" * 2 is
    '4545'. max(["9", "45", "100"]) is '9', because strings
    compare character by character and '9' sorts after '1'. Sorting a column
    of string numbers silently gives the wrong order and no error at all — which you discover three
    steps later, in a chart.

  


  

    
Convert at the boundary

    
Convert every field to its real type at the moment you read it, in the loader,
    once — never further downstream. After the loader, the rest of your program should be able to
    assume entry.minutes is an int and never check again.

    
That is Part 3's “fail early” applied to data: the loader is the boundary
    between the messy outside world and your clean inside one, and boundaries are where validation
    belongs.

  


  
Conversion is also where bad data announces itself, so this is the natural home for a named
  exception carrying the row number:


  
class InvalidEntryError(ValueError):
    """A CSV row we refuse to accept."""

def load_minutes(path):
    """Return (name, minutes) pairs from path, naming any unusable row."""
    pairs = []
    with open(path, encoding="utf-8", newline="") as f:
        for number, row in enumerate(csv.DictReader(f), start=2):   # line 1 is the header
            try:
                minutes = int(row["minutes"])                       # convert at the boundary
            except ValueError as error:
                raise InvalidEntryError(
                    f"row {number}: bad minutes {row['minutes']!r}"
                ) from error                                        # keep the original cause
            pairs.append((row["name"], minutes))
    return pairs


  
start=2 is not a typo: line 1 is the header, so the first data row is line 2 and the
  number in the message matches what your editor shows. from error — chaining, from
  Part 3 — preserves the original ValueError, so the traceback
  shows both the row you can go and fix and the int() call that objected. To skip bad rows
  rather than stop, replace the raise with a print and a
  continue, as load_scores did.

Why classes exist


  
Everything so far has kept data in one place and behaviour in another: data in
  variables, lists, and dictionaries; behaviour in functions that take that data as arguments. This
  part shows the point where that split stops working, and the tool Python offers instead. You need
  it for one very practical reason — from Module 11 onwards, every model you use is written like
  this:

Three lines, and every idea in Parts 6 and 7 is hiding in them.

Suppose you are tracking study sessions — who studied, when, for how long, on what topic. With
  only Modules 01-02 behind you, the obvious approach is one list per field:

  duration. Two lists that must stay in the same order are a promise the language cannot enforce, and
  every extra field is one more list that can slip.

  you need. But it leaves the behaviour homeless: the rule “a session's length in hours is its
  minutes divided by 60” gets retyped as s["minutes"] / 60 in five places, so changing it
  means five edits and four chances to forget one. Nor does anything say which keys a record must have,
  so a forgotten "topic" or a misspelled s["minute"] only surfaces later as a
  KeyError.

  kind has and what that record can do:


  
class StudyEntry:
    """One study session: who studied, when, for how long, on what."""

    def __init__(self, name, date, minutes, topic):
        """Store the four fields of one session."""
        self.name = name
        self.date = date
        self.minutes = minutes
        self.topic = topic

    def hours(self):
        """Return this session's length in hours."""
        return self.minutes / 60

    def summary(self):
        """Return one printable line about this session."""
        return f"{self.name} studied {self.topic} for {self.hours():.2f} h"

Class, instance, instantiation


  
Three words, one idea. They are worth getting exactly right, because every error message and
  every library page uses them.


  
    
    
  • The class is the blueprint. StudyEntry is a class: a
    description of what a session is and what it can do. It holds no data about maya, and reading a
    class statement creates nothing but the description — like a house blueprint, which
    nobody can live in.
    • 
    
  • The instance is the thing. entry is an instance (also:
    an object): one actual session, with maya's name and 45 in it. One class can have
    thousands of instances, each holding its own values.
    • 
    
  • Calling the class builds one. StudyEntry("maya", …) is
    instantiation: calling the class like a function to get a new instance back. This is the
    only step that creates data.
    • 
  


  
Class names use CapWords by convention, while functions and variables use
  snake_case. That convention does real work: reading
  train_test_split(X, y) you know a function is being called; reading
  StandardScaler() you know a class is being instantiated and an object is coming
  back.


  
Attributes and methods


  
An instance carries two kinds of thing, and both are reached with a dot.


  
    
    
  • An attribute is a value stored on the instance: entry.name,
    entry.minutes. No parentheses — you are reading a value, not calling anything.
    • 
    
  • A method is a function defined inside the class and called on an instance:
    entry.hours(). Parentheses, because you are calling it.
    • 
  


  
The parentheses are not a style choice. entry.hours() is 0.75, while
  entry.hours is <bound method StudyEntry.hours of <__main__.StudyEntry object
  at 0x…>> — the method object itself. Forgetting them raises nothing at the time, and
  surfaces later as something baffling like
  TypeError: unsupported operand type(s) for /: 'method' and 'int'. If a value ever prints
  as <bound method …>, you left off a ().

__init__ and self


  
Two pieces of syntax do almost all the work in a class, and both look strange the first time.
  Take them one at a time.


  
__init__ runs at instantiation


  
__init__ — two underscores, the word “init”, two underscores — is the method Python
  calls for you the moment an instance is created. Its job is to put the instance's starting
  attributes on it. You never call it yourself; writing StudyEntry(…) calls it.


  

    
class StudyEntry:
    def __init__(self, name, minutes):
        self.name = name
        self.minutes = minutes

    

      
class is the keyword that starts a
      class definition, exactly as def starts a function definition. Like
      def, it runs once and creates only the blueprint.

      
StudyEntry is the class's name, in
      CapWords. The colon ends the header line and announces an indented block, as with
      if, for, and def.

      
def inside a class body defines a
      method rather than a plain function. Nothing else changes: same parameters, same
      return.

      
__init__ is the initialiser. Python
      calls it automatically at instantiation, handing it the brand-new instance. It must not
      return a value — instantiation already gives the instance back.

      brand-new instance. The name is a convention rather than a rule, but a convention with no
      exceptions: call it self. name, minutes are ordinary parameters, filled from the call in

      creates an attribute named name on the instance. The right side
      reads the parameter name, which vanishes when __init__
      returns. Drop the self. and you assign a local variable that is thrown away one line
      later.

    

  


  
self is the instance, and the dot supplies it


  
This is the sentence that dissolves every self confusion, so read it slowly:
  a method call written with a dot passes the object on the left of the dot as the first
  argument. That is the entire mechanism. self is not magic, not a keyword, and
  not a special variable — it is parameter number one, and the dot fills it in.


  

    
The rule: entry.total() is StudyEntry.total(entry)

    entry's class and calls it with entry as the first argument. These two
    lines are the same call, and either one is legal to type:

So inside a method body, self is this particular instance — whichever one
    was on the left of the dot. self.minutes means “the minutes attribute of
    the entry I was called on”.

  an argument whether you declared a slot for it or not. Second: to reach the instance's data from

  minutes into self.minutes. Module 02's LEGB rule still governs bare names,
  and attributes are not part of it.

Attributes exist because something assigned to them


  
There is no list of permitted attributes anywhere in a class. An attribute exists on an instance
  from the moment some line assigns to it, and not one instant earlier. That single fact turns
  AttributeError from a mystery into a question about order:


  
class StudyEntry:
    def __init__(self, name, minutes):
        self.name = name
        self.minutes = minutes       # note: no topic

entry = StudyEntry("maya", 45)

  File "entry.py", line 7, in <module>
    print(entry.topic)
          ^^^^^^^
AttributeError: 'StudyEntry' object has no attribute 'topic'


  
Read that as a factual report, not an accusation: nothing has assigned
  entry.topic yet. Three things cause it. A typo — you wrote
  entry.topics and __init__ assigned self.topic. A missing
  assignment — the case above. Or, most importantly, wrong order: the assignment lives
  in some other method that has not run yet. That third case is the whole story behind
  AttributeError: 'MeanMinutesModel' object has no attribute 'mean_' in
  Part 7 — fit is what creates mean_, so calling
  predict first finds nothing there. You can always check what an instance actually has,
  because Python keeps its attributes in an ordinary dictionary called __dict__:
  print(entry.__dict__) gives {'name': 'maya', 'minutes': 45}. That is not a
  metaphor; it is literally where they live.


  
Methods that use other methods


  
A method can call another method on the same instance through self, exactly as
  outside code would through a variable name. In the StudyEntry at the top of this part,
  summary never repeats self.minutes / 60 — it calls
  self.hours(). That is the payoff promised earlier: the hours rule lives in exactly one
  method, and every other method plus every line outside the class goes through it, so changing
  hours corrects every caller at once. The self. is not decoration — plain
  hours() raises NameError: name 'hours' is not defined, because
  hours is an attribute of the class, not a global function. Same rule as before, one
  layer up.

Instance attributes vs class attributes


  
Every attribute so far was created with self.something = … inside
  __init__, which makes it an instance attribute: one copy per instance, so
  maya's entry and ravi's entry each have their own. There is a second kind, and it behaves
  differently in a way that produces one of the nastiest bugs in beginner Python.


  
One per instance, or one for everybody


  
A class attribute is assigned in the class body, outside any method. There is exactly
  one of it, stored on the class, and every instance sees that same one:

  self.GOAL_MINUTES. That works because of one small rule with large consequences:


  

    
The lookup rule: instance first, then class

    
obj.name looks for name in the instance's own
    __dict__ first. If it is not there, Python looks on the instance's class. If it is
    not there either, you get AttributeError.

    
So a class attribute acts as a default that every instance sees, and an instance
    attribute of the same name hides it — for that one instance only. This is Module 02's
    LEGB shadowing idea, applied to dots instead of bare names.

  


  
Class attributes are the right home for constants belonging to the concept rather than to one
  record: a goal, a limit, a format string, the list of valid column names. Name them in
  UPPER_SNAKE_CASE when they are constants, and read them through self. so
  that a subclass can override them (Part 7).


  
Assigning through an instance never touches the class. maya.GOAL_MINUTES = 60
  creates a brand-new instance attribute on maya that shadows the shared one; ravi still
  finds 30, and so does StudyEntry.GOAL_MINUTES. Demo 8 below lets you watch that happen.
  Which brings us to the case where the same rule bites.

Dunder methods: plugging into Python's syntax


  
You have now met three names shaped like __init__, __dict__,
  __main__. A dunder method (short for “double underscore”) is a method with
  two leading and two trailing underscores that Python calls for you in response to ordinary
  syntax, rather than one you call by name. __init__ is the one you already know: you
  never call it, and instantiation calls it. There are dozens more, and together they answer a
  question you will have in Module 07 — how can a + b possibly mean “add two whole
  arrays”?


  
__repr__ for you, __str__ for the user


  
Start with the two that pay for themselves immediately. Print an instance of a class with no
  dunders and you get Python's fallback — the class it belongs to and its address in memory:

<__main__.StudyEntry object at 0x0000014245238830>

The hexadecimal number differs on every run, which tells you it is useless for reading and
  useless for comparing runs. A list of eight entries prints as eight of these. Every time you print
  a data structure while debugging, you pay that tax.


  
__repr__ removes it: it returns a string a programmer finds useful, by
  convention one that looks like the call that would rebuild the object. __str__ is the
  friendly twin, used by print(), str(), and f-strings when it exists.
  Define __str__ only when the readable form genuinely differs from the debugging
  form:


  
class StudyEntry:
    def __init__(self, name, minutes):
        self.name = name
        self.minutes = minutes

    def __repr__(self):
        return f"StudyEntry(name={self.name!r}, minutes={self.minutes!r})"

    def __str__(self):
        return f"{self.name}: {self.minutes} min"

entry = StudyEntry("maya", 45)
print(entry)              # __str__
print(repr(entry))        # __repr__
print([entry])            # containers always use __repr__

[StudyEntry(name='maya', minutes=45)]


  
The !r inside the f-string is worth stealing. It means “use repr() of
  this value, not str()”, which is why the name comes out as 'maya' with
  quotes and the minutes come out as bare 45. That is Part 3's
  print(repr(x)) advice, applied inside your own class: quotes tell you the value is a
  string, and a string where you expected a number is the root cause of half of all
  CSV bugs.


  

    
Write __repr__ first, and often only __repr__

    
A class with __repr__ but no __str__ falls back to
    __repr__ for print() — so one method covers both jobs. The reverse is
    not true: a class with only __str__ still shows
    <… object at 0x…> inside lists and dicts, which is exactly where you most need
    to read it.

    Optional deep dive __eq__, hashability, and the dataclasses shortcut
    

      
The default == is identity. Without __eq__, two
      instances are equal only when they are literally the same object, so
      StudyEntry("maya", 45) == StudyEntry("maya", 45) is False and a set of
      those two holds two items. That is often what you want for records representing distinct events.
      But if two entries with the same fields should count as the same entry — for the
      deduplication challenge in the notebook, say — you must say so, by defining __eq__
      to compare the fields you care about.

      
Defining __eq__ makes your class unhashable, which surprises
      everyone the first time:

Module 02's deep dive explained why: a set or dict key picks its slot from
      hash(x), and equal objects must hash alike or lookups break. Python cannot guess how
      your new __eq__ maps onto a hash, so it withdraws the default rather than let it be
      silently wrong. If you need the objects in a set, add __hash__ too — usually
      return hash((self.name, self.date)), a tuple of the same fields
      __eq__ compares. If you do not, ignore the whole issue.

      dataclasses module writes __init__, __repr__, and
      __eq__ for you from a list of field names: @dataclass above

      becomes five. It is genuinely good, and worth adopting once plain classes feel ordinary. It is
      not taught here because it hides precisely the mechanics — where attributes come from, what

Overriding a method


  
Define a method in the child with the same name as one in the parent and the child's version wins
  for child instances. This is method overriding; the child is said to
  override the parent's method. The parent is untouched, so its own instances behave
  exactly as before:


  
class GroupStudyEntry(StudyEntry):
    """A session studied together with other people."""

    def label(self):
        """Return the parent's line, plus who else was there."""
        return super().label() + " (with ravi, ada)"

  extend the original instead of replacing it, which is nearly always what you want: the
  parent keeps owning the part it knows about, and the child adds only its own contribution.

Where you have already seen this: the project's exception classes


  
You met inheritance in Part 2 without the word. KeyError is
  a subclass of LookupError, which is a subclass of Exception — and that is
  precisely why except LookupError: catches a KeyError. The exception tree is
  a class hierarchy, and except asks “is this exception an instance of that class, or of
  any of its subclasses?”


  
Part 3 promised that this module's project would define its own exceptions
  and that Part 7 would explain the mechanics. Here they are — three lines, and they are the real ones

class StudyLogError(Exception):
    """Base class for every failure this project raises."""


class InvalidEntryError(StudyLogError, ValueError):
    """A row we refuse to accept."""


class NotFittedError(StudyLogError):
    """predict() or score() was called before fit()."""


  
A class body containing only a docstring is complete and idiomatic; these classes need no methods
  because Exception already supplies everything — storing a message, printing it,
  args, and the whole traceback machinery. All you are adding is a name, and a
  name is exactly what a caller needs in order to catch this failure and not others.


  
StudyLogError(Exception) gives the project one family. A caller who wants to survive
  anything this project deliberately raises writes except StudyLogError: — one clause,
  covering all three — while still letting a genuine bug such as a TypeError crash
  loudly, which is what Part 2 asked for.


  

    
The two-parent line, in plain words

    
class InvalidEntryError(StudyLogError, ValueError): lists two parents, and it means
    what it looks like: an InvalidEntryError is a
    StudyLogError and is a ValueError. So a caller can catch
    ValueError or StudyLogError and either one works — you do not have
    to guess which they will write:

That is a kindness, not a trick. “Bad value” code everywhere in Python already catches
    ValueError, so inheriting from it means your exception fits code that was written
    before your project existed. Two parents is as far as this course goes; you never need more, and
    you never need to know the order Python searches them in.

Three ways inheritance goes wrong

    
Forgetting super().__init__(). The symptom is an
    AttributeError for an attribute the parent was supposed to set, raised from a method
    that looks innocent. Check the child's __init__ first, every time.

    
Inheriting in order to reuse one helper. If you only want the parent's
    total_minutes method, subclassing drags in its entire interface and its future
    changes, and claims a relationship that is not true. Use composition instead — the next
    section.

    
Deep hierarchies. Four levels of subclass means finding a method requires
    reading four files. Two levels is plenty for everything in this course. If you find yourself
    drawing a family tree to answer “what does this method do”, the design is wrong, not your
    reading.

Has-a beats is-a


  
Composition means one object holds another as an attribute, instead of being a
  kind of it. It is the right answer far more often than inheritance, and the test is a sentence you
  say out loud. “A group study session is a study session” — true, so inherit. “A study log
  is a list” — false. A study log has a list:


  

    

      
Inheritance — claims something untrue

log.pop()           # inherited

Composition — exposes only what you meant

      
class StudyLog:
    """A collection of study entries."""

    def __init__(self):
        self.entries = []          # HAS a list

    def add(self, entry):
        """Append one entry."""
        self.entries.append(entry)

    def total_minutes(self):
        """Return the summed minutes of every entry."""
        return sum(e.minutes for e in self.entries)

    

  


  
The left column inherits about forty list methods, all of them public, most of them meaningless
  for a log and one of them (clear) actively dangerous. The right column offers exactly
  the two operations a log should support, and can change how entries are stored — to a dict keyed by
  name, say — without breaking a single caller. The project's StudyLog is built the second
  way, and the Part 9 rubric awards a point for it.


  
isinstance(x, Class)


  
isinstance asks whether an object belongs to a class or to any of its
  subclasses. That “or subclasses” is the whole point, and it is the same rule
  except uses:

print(isinstance(group, GroupStudyEntry))   # True
print(isinstance(group, StudyEntry))        # True  -- a subclass instance IS a parent instance
print(type(group) is StudyEntry)            # False -- type() is exact, isinstance is not

error = InvalidEntryError("bad row")

print(isinstance(error, StudyLogError))     # True


  
Prefer isinstance(x, C) over type(x) is C, because the second quietly
  rejects subclasses. And use it sparingly: needing to ask an object what class it is usually means the
  object should have had a method you could just call.


  
Duck typing


  
Duck typing is the habit of judging an object by the methods it has rather than the
  class it belongs to — “if it walks like a duck and quacks like a duck, treat it as a duck”. Python
  does this everywhere. len(x) does not check whether x is a list; it calls
  x.__len__() and works for anything that defines it, which is why the
  StudyLog in Part 6 could be measured without inheriting from anything.


  
This is not a curiosity. It is precisely why scikit-learn will accept the class you are about to
  write. A function like cross_val_score(model, X, y) never asks
  isinstance(model, SomeBaseClass). It calls model.fit(...), then
  model.predict(...), then model.score(...). Any object with those methods
  works — including yours:


  
def evaluate(model, entries):
    """Fit any model-shaped object and report its error. No class is named."""
    model.fit(entries)
    return model.score(entries)


  
That function is nine words of docstring away from being real library code, and it will keep
  working when you swap MeanMinutesModel for a real regressor in Module 11. The
  shape is the interface. The next section is that shape.

  in this course is used in three steps, and you can now name all three:

  the reason they can talk to each other at all is that fit stores its result on
  self, where predict can read it back. That is the whole design, and it
  is why models are objects and not functions: a function would have to hand its learning back to you
  and take it as an argument next time.


  
Here is the complete class. Twenty lines, and it is a genuine, usable model:


  
import statistics


class MeanMinutesModel:
    """Predict every session's minutes as the centre of the training minutes."""

    def __init__(self, strategy="mean"):
        """Store the strategy to use. Nothing is learned here."""
        self.strategy = strategy

    def fit(self, entries):
        """Learn the centre of entries' minutes, store it, and return self."""
        minutes = [entry.minutes for entry in entries]
        if self.strategy == "mean":
            self.mean_ = sum(minutes) / len(minutes)
        elif self.strategy == "median":
            self.mean_ = statistics.median(minutes)
        else:
            raise StudyLogError(f"unknown strategy: {self.strategy!r}")
        return self

    def predict(self):
        """Return the learned prediction. Raise NotFittedError if unfitted."""
        if not hasattr(self, "mean_"):
            raise NotFittedError("call fit(entries) before predict()")
        return self.mean_

    def score(self, entries):
        """Return the mean absolute error of this model on entries."""
        guess = self.predict()
        errors = [abs(entry.minutes - guess) for entry in entries]
        return sum(errors) / len(errors)

    def __repr__(self):
        return f"MeanMinutesModel(strategy={self.strategy!r})"


  
Read it once more and count the Module 02 skills doing real work: a list comprehension, a
  conditional, sum and len, an f-string. There is nothing in this class you
  could not have written a week ago. What is new is the shape.


  
__init__ stores your choices; fit stores what the data taught


  

    
The most important distinction in this module

    
A hyperparameter is a setting you chose. It is passed to
    __init__, stored without a trailing underscore, and would be the same whether you had
    ten rows of data or ten million. strategy="mean" is one.

    
A fitted attribute (or learned parameter) is a value the data
    decided. It is created by fit, named with a trailing
    underscore, and does not exist until fit has run. mean_ = 45.0 is
    one.

    
So: __init__ stores what you chose; fit stores what the data
    taught, with a trailing underscore, and returns self. Every module from 11
    onwards assumes you know which of an object's attributes is which — because tuning a model means
    changing hyperparameters, and interpreting a model means reading fitted attributes.

  


  
The rule holds all the way up. Ridge(alpha=0.5) — you chose alpha, and
  no amount of data will change it. KMeans(n_clusters=3) — you chose 3. After
  .fit(X, y), ridge.coef_ and kmeans.cluster_centers_ exist, and
  those came from the data. The line between the two is the line between
  tuning and training.


  
The trailing underscore


  
One character carries the whole convention, and it is doing three jobs. It tells a reader that the
  value was learned rather than chosen. It tells them the attribute may not exist yet. And it keeps the
  learned value from colliding with the hyperparameter that produced it. Once you know it, a
  scikit-learn object's attribute list reads as documentation:


  

    
AttributeWhich kindWhere it came from

    
      
strategyHyperparameterYou passed it to __init__

      
alpha, n_clusters, max_depthHyperparameterYou passed it to __init__

      
mean_FittedYour fit computed it

      
coef_, intercept_FittedA regression learned them from X and y (Module 11)

      
n_features_in_Fittedfit counted the columns it was given

      
classes_Fittedfit discovered which labels exist (Module 16)

    
  


  
When a library page lists “Attributes: coef_, intercept_”, it is telling
  you what became available after fit. The convention is the documentation.


  
fit returns self


  
fit ends with return self. It has already done its work by mutating the
  instance, so it has nothing else to hand back — and returning the object itself makes the call
  chainable:


  
model = MeanMinutesModel().fit(entries)          # instantiate and fit in one line
print(MeanMinutesModel().fit(entries).predict())  # 45.0

m = MeanMinutesModel()
print(m.fit(entries) is m)                       # True -- the same object, not a copy


  
That True is the point, and it is a trap in disguise: fit does
  not return a new fitted model, it returns the one you already had, changed. Writing
  fitted = model.fit(entries) gives you two names for one object — Module 02's aliasing,
  one more time. There is only ever one model.

What should predict() do on a model that has never been fitted? Part 3 already answered: not return None, which would relocate the
  crash to somewhere confusing, and not return 0, which would silently poison every number downstream.
  It should raise, with a name and an instruction:


  
    def predict(self):

        if not hasattr(self, "mean_"):
            raise NotFittedError("call fit(entries) before predict()")
        return self.mean_

  situation. Only the second one tells you the fix, and only the second one can be caught with

  own NotFittedError for exactly this reason, and its message names the class and the
  method — which is why hasattr(self, "mean_") at the top of predict is not
  defensive clutter but the single most professional line in the class.


  
score, and transform for things that reshape rather than predict


  
score(data) returns one number saying how well the model does on that data, so you
  can compare two models with one line each. Ours returns the mean absolute error — the
  average distance between the prediction and the truth — where lower is better. On the three sessions
  [45, 30, 60], a prediction of 45.0 is out by 0, 15, and 15, so the score is
  10.0. On all eight rows of sample_log.csv it is 22.5. Beware:
  scikit-learn's own .score() conventionally returns a number where higher is
  better, so always check which direction a score runs before you celebrate.
  Module 15 is about doing this
  honestly — on data the model has never seen.

A module is a Python file


  
A module is a .py file you can import. That is the whole definition:
  csv is a file called csv.py sitting in your Python installation, and
  study_tracker.py is a module too, the moment anything imports it.


  
import math does exactly two things. It runs the file — once, top to bottom — and it
  binds one name, math, in your namespace. That name is a
  module object (type(math) is <class 'module'>), and
  everything the file defined is an attribute on it, reached with the dot you now understand:
  math.sqrt(2) gives 1.4142135623730951.


  
“Runs the file once” matters. A second import math anywhere in your program does not
  re-run anything; Python remembers modules it has already loaded and hands back the same object. This
  is why a module that prints something at the top level prints it only once, and it is behind the
  live-kernel trap in the pitfall box below.


  
The four forms, and which to prefer


  

    
FormWhat it bindsUse it when

    
      

        import math
        One name: math
        The default. Every use says where it came from, so math.sqrt can never be confused with your own sqrt.
      

      

        import numpy as np
        One name: np
        When the name is long and the community has a standard alias — np, pd, plt. Never invent your own alias for a well-known library.

Four import traps

    
Naming your file after a standard-library module. Save a file as
    random.py or csv.py or json.py in your project folder, and
    your file is found first — for you and for every library that tries to import the real one:

    
AttributeError: module 'random' has no attribute 'randint'

    
Python 3.13 and later add a hint naming the offending file. Earlier versions leave you staring
    at an impossible message. Rename the file and delete any __pycache__ folder beside
    it.

    
from module import *. It hides where names came from and lets one
    module silently overwrite another's. There is no situation in this course where it is the right
    choice.

    
Editing a module and re-importing it in a live kernel. Because
    import runs a file only once, a second import gives you the
    old code, and you will debug a fix that is already correct on disk.
    Restart the kernel after editing an imported file.

    
Circular imports. If a.py imports b.py and
    b.py imports a.py, one of them will be half-built when the other reads
    it, producing ImportError: cannot import name 'X' from partially initialized module.
    The fix is structural: move the shared thing into a third module both can import.

__pycache__


  
The first time you import a module, Python compiles it to bytecode and caches the result in a
  __pycache__ folder next to the file, so later imports start faster. You never edit it,
  never commit it, and never need to think about it — this course's .gitignore already
  excludes it. The one time it matters is the stale-cache case above: if you deleted a
  .py file and its import still seems to work, delete __pycache__.


  

    Optional deep dive What import actually does, step by step
    

      
The sequence. import study_tracker does five things. It checks
      sys.modules, a dictionary of everything already imported — if the name is there,
      nothing else happens and you get that object back. Otherwise it walks sys.path in
      order looking for study_tracker.py (or a folder of that name containing modules). It
      creates an empty module object. It executes the file top to bottom with that module as the
      namespace, so every def, class, and assignment becomes an attribute of
      it. Finally it records the module in sys.modules and binds the name in your
      namespace.

      
Step four is why the if __name__ == "__main__": guard exists: importing
      runs the file, so anything at the top level happens to whoever imports you. Step one is
      why editing a module has no effect in a live kernel — the name is already in
      sys.modules, so the file is never re-read. (importlib.reload exists and
      is more trouble than restarting.)

      
Reading the standard library. Every pure-Python module tells you where it
      lives: csv.__file__ is C:\Python313\Lib\csv.py. That is an ordinary text
      file, written in the Python you have been learning, and reading it is a genuinely useful hour — it
      is well-commented, it uses classes exactly as Part 6 taught them, and it is a realistic sample of

Milestone 2 · the exception family, and validation in __init__

  
Three classes, one family. InvalidEntryError has two parents, so a caller can
  write except StudyLogError or except ValueError and either one
  works.

  
GOAL_MINUTES = 30
MAX_REASONABLE_MINUTES = 1440      # 24 hours; anything longer is a typo


class StudyLogError(Exception):
    """Base class for every failure this project raises on purpose."""


class InvalidEntryError(StudyLogError, ValueError):
    """A row we refuse to accept. Also a ValueError, so either catch works."""


class NotFittedError(StudyLogError):
    """Raised when a model is asked to predict before it has been fitted."""


def parse_minutes(text):
    """Return text as a whole number of minutes, or raise InvalidEntryError."""
    try:
        minutes = int(text)
    except (TypeError, ValueError) as error:
        raise InvalidEntryError(f"minutes must be a whole number, got {text!r}") from error
    if minutes < 0:
        raise InvalidEntryError(f"minutes cannot be negative, got {minutes}")
    if minutes > MAX_REASONABLE_MINUTES:
        raise InvalidEntryError(f"minutes must be at most {MAX_REASONABLE_MINUTES}, got {minutes}")
    return minutes


class StudyEntry:
    """One study session: who studied, when, for how long, and on what."""

    def __init__(self, name, date, minutes, topic):
        """Store one validated session. Raises InvalidEntryError on bad input."""
        self.name = str(name or "").strip()
        if not self.name:
            raise InvalidEntryError("name cannot be blank")
        self.date = str(date or "").strip() or "unknown"
        self.minutes = parse_minutes(minutes)     # converts AND validates, in one place
        self.topic = str(topic or "").strip() or "unlabelled"

    def hours(self):
        """Return the session length in hours, rounded to two decimals."""
        return round(self.minutes / 60, 2)

    def met_goal(self, goal=GOAL_MINUTES):
        """Return True when this session reached the goal."""
        return self.minutes >= goal

    def __repr__(self):
        return (f"StudyEntry(name={self.name!r}, date={self.date!r}, "
                f"minutes={self.minutes!r}, topic={self.topic!r})")

  self.entries is created inside __init__, never at class level.

  
class StudyLog:
    """A collection of StudyEntry objects. It HAS a list; it is not a list."""

    def __init__(self, entries=None):
        """Start empty, or from an existing iterable of entries."""
        self.entries = list(entries) if entries else []      # built here, never shared

    def add(self, entry):
        """Append one StudyEntry. Raises InvalidEntryError for anything else."""
        if not isinstance(entry, StudyEntry):
            raise InvalidEntryError(f"expected a StudyEntry, got {type(entry).__name__}")
        self.entries.append(entry)

    def names(self):
        """Return every learner name once, sorted."""
        return sorted({entry.name for entry in self.entries})

    def for_name(self, name):
        """Return the list of entries belonging to one learner."""
        return [entry for entry in self.entries if entry.name == name]

    def total_minutes(self, name=None):
        """Return total minutes for one learner, or for everybody when name is None."""
        chosen = self.entries if name is None else self.for_name(name)
        return sum(entry.minutes for entry in chosen)

    def summary(self):
        """Return {name: {sessions, total, average, best, days_at_goal}} for every learner."""
        report = {}
        for name in self.names():
            sessions = self.for_name(name)
            minutes = [entry.minutes for entry in sessions]
            report[name] = {
                "sessions": len(minutes),
                "total": sum(minutes),
                "average": round(sum(minutes) / len(minutes), 2),
                "best": max(minutes),
                "days_at_goal": len([entry for entry in sessions if entry.met_goal()]),
            }
        return report

    def __len__(self):
        return len(self.entries)

    def __repr__(self):
        return f"StudyLog({len(self.entries)} entries, {len(self.names())} learners)"

def load_log(path=SAMPLE_LOG_PATH):
    """Return a StudyLog of every valid row, reporting each row it skips."""

import json


def save_summary(log, path):
    """Write log.summary() to a JSON file with indent=2 and return the path."""
    path = Path(path)
    path.parent.mkdir(parents=True, exist_ok=True)     # the folder may not exist yet
    with path.open("w", encoding="utf-8") as handle:   # "w" truncates: intended here
        json.dump(log.summary(), handle, indent=2)
    return path

Milestone 6 · MeanMinutesModel, the shape of every model to come

  under a name ending in an underscore, and returns self.

  
import statistics


class MeanMinutesModel:
    """A baseline that predicts one number of minutes for every learner."""

    def __init__(self, strategy="mean"):
        """Store the choice you made. Nothing is learned yet."""
        if strategy not in ("mean", "median"):
            raise StudyLogError(f"strategy must be 'mean' or 'median', got {strategy!r}")
        self.strategy = strategy          # hyperparameter: you chose it

    def fit(self, entries):
        """Learn one number from the entries, store it as mean_, and return self."""
        minutes = [entry.minutes for entry in entries]
        if not minutes:
            raise InvalidEntryError("cannot fit on an empty list of entries")
        if self.strategy == "median":
            self.mean_ = float(statistics.median(minutes))
        else:
            self.mean_ = statistics.fmean(minutes)
        return self                       # so Model().fit(entries).predict() works

    def predict(self):
        """Return the learned prediction. Raises NotFittedError before fit()."""
        if not hasattr(self, "mean_"):
            raise NotFittedError("call fit(entries) before predict()")
        return self.mean_

    def score(self, entries):
        """Return the mean absolute error of this prediction on entries."""
        prediction = self.predict()
        minutes = [entry.minutes for entry in entries]
        if not minutes:
            raise InvalidEntryError("cannot score on an empty list of entries")
        return statistics.fmean(abs(m - prediction) for m in minutes)

    def __repr__(self):
        return f"MeanMinutesModel(strategy={self.strategy!r})"


try:
    MeanMinutesModel().predict()          # nothing has been learned yet
except NotFittedError as error:

REPORT_WIDTH = 52


def class_totals(log):
    """Return (learner_count, total_minutes, sessions_at_goal) for a whole log."""
    summary = log.summary()
    return (
        len(summary),
        sum(figures["total"] for figures in summary.values()),
        sum(figures["days_at_goal"] for figures in summary.values()),

def print_report(log, goal=GOAL_MINUTES):
    """Display the log as a table. This is the only function here that prints."""
    print("STUDY TRACKER")
    print("=" * REPORT_WIDTH)

        print("No usable entries in the log yet.")
        return

    ranked = sorted(summary, key=lambda name: summary[name]["total"], reverse=True)
